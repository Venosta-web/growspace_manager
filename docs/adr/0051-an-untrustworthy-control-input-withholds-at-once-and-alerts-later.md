# An Untrustworthy Control Input Withholds at Once, and Alerts Later

**Status:** Accepted

Crop steering read the moisture sensor's last state however old and however strange it was. A probe that froze at a dry value — the usual failure of a Zigbee or MQTT sensor without availability reporting — kept firing a shot every interval, and a probe pulled out of the substrate reading `0` looked bone-dry and did the same (#789). ADR-0050 fixed the tank half of that and put the rules in `domain/sensor_validity.py`; this decision extends the same module to every [[Control Input]] rather than growing a second one.

**The window is learned, not configured per sensor.** The glossary already defined the right one — the [[Observation Validity Window]], three expected update intervals under a cap — but nobody knows a sensor's expected interval, and asking a grower for it per sensor is a setting nobody would fill in. So the watch learns it: the median of the last eight intervals between the sensor's `last_reported` stamps, trusted after three, never under five minutes, never over `sensor_stale_after_minutes` (default 30). A probe that reports every two minutes is stale six minutes after it stops rather than thirty, and one that reports every half hour is capped rather than tolerated for ninety. Only numeric reports teach the cadence, so a sensor that flaps to `unavailable` does not look like one that reports often. It is kept in memory: after a restart the cap alone applies until three reports have been seen, which errs long, not short. Freshness is `last_reported`, as for tanks, so a steady sensor that is still speaking is never stale. The cap is one setting per growspace because the question it answers — "how long is too long to act on a moisture reading?" — is about the tent, not the probe; `0` turns it off for a probe that genuinely reports only on change.

**Shots stop at once; the alert waits.** A tank gets a grace period in which its last reading stands in (ADR-0050), because a tank's level moves slowly and refusing on a twelve-second dropout would stop a tent for nothing. A moisture reading is the trigger itself: the last value before a probe froze is exactly the value that would keep firing. So the steering loop decides nothing on an invalid reading and the [[Irrigation Controller]] reads `inhibited` with `sensor_stale`, `sensor_implausible` or `sensor_unavailable` from the first minute, while the alert — one push per episode on its own tier, a persistent notification, and a recovery message — waits `sensor_alert_delay_minutes` (default 15), so a short dropout withholds a shot silently rather than paging. The episode is a `SensorWatch`, the `TankWatch` pattern without the grace, with the same 60-minute re-alert limit; the Safety Ledger gets one entry per edge, not one per minute. Manual runs are not held, as with the [[Startup Inhibit]]: they are an explicit human action by someone who can look at the pot.

**Zero is a reading unless the grower says otherwise.** A capacitive probe in a truly dry pot can read 0, and refusing to water it would kill the plant the check is meant to protect. A probe pulled out into air reads 0 as well, and that is the failure the issue names. Neither is distinguishable from the number, so `moisture_zero_is_implausible` is an opt-in, off by default, which keeps today's behaviour for everyone who has not seen the second failure.

**Pore EC is validated but never holds irrigation.** It modulates shot size; it does not trigger shots. An invalid probe is left out of the average (a µS/cm probe is converted first rather than read as a thousand times too salty), and with none left modulation is simply off. Holding irrigation on a dead EC probe would trade a missing refinement for missing water.

**Climate reads get plausibility now, freshness with #792.** The exhaust fan and the VPD on/off controllers read through the same helper, so an out-of-range humidity or a VPD in pascals is `None` — the path they already take for an unavailable sensor — rather than demand. Temperature ranges follow the sensor's own unit and values are never converted, since targets are set in the same unit. What those controllers should _do_ when their input stops reporting — fail-safe states and actuator interlocks — is a behaviour change of its own and belongs to #792, which will pass a validity window to the same function.
