# Grow Light Controller Re-pushes the AC Infinity Schedule via a Self-Owned Midnight/Startup Re-derivation

ADR-0023 established that the AC Infinity grow-light path is a *configurator*: GSM writes the device's onboard `Schedule` (on/off `time` entities, `on_power`, sunrise) once and lets the device run the cycle autonomously. Because the device runs the cycle itself, GSM must re-push whenever the *derived* photoperiod changes — specifically the veg→flower flip, which shrinks the light day 18h→12h (`cycle_end = lights_on_time + (flower_day_hours if any plant has entered flower else veg_day_hours)`). ADR-0023 explicitly left the *trigger* for that re-push unresolved: `PhotoperiodFlipChecker` only calls `async_send_notification` and exposes no event or hook to subscribe to. This ADR resolves that open question.

**Decision: the Grow Light Controller owns its own re-derivation timer.** It mirrors `PhotoperiodFlipChecker.schedule_growspace` — a one-shot `async_track_point_in_utc_time` at the next local midnight that reschedules itself, plus an immediate startup pass — and, on each firing, re-derives the desired schedule and **re-pushes to the device only if it differs** from what the device currently holds (idempotent reconcile, not an unconditional write). The same reconcile runs on **config save** (the user edited power, sunrise, or `lights_on_time`). `PhotoperiodFlipChecker` is left untouched.

## Considered Options

- **Extend `PhotoperiodFlipChecker` to drive the controller's re-push.** Rejected. It already iterates growspaces at midnight + startup, so it looks like the natural home — but it would couple a *notification* subsystem to an *actuator* subsystem, and its predicate is the wrong one: it fires on `flower_start == today` ("flipped *today*"), whereas the grow light's `cycle_end` depends on `flower_start <= today` ("*entered* flower"). The two share the `veg/flower_day_hours` source but ask different questions (see the **Grow Light Controller** glossary term), so overloading the flip checker would either mis-fire or force it to grow a second predicate it does not otherwise need. A missed or mistimed event here leaves a stale, too-long photoperiod on the hardware — the exact dark-period-integrity failure the design exists to prevent — so the trigger must be robust, not incidental.
- **A one-shot event fired at the flip.** Rejected. An edge-triggered "flip happened" event is fragile across restarts and clock changes: if HA is down over the midnight the flip lands on, the event is simply lost and the device keeps the veg-length schedule until something else re-pushes. An idempotent level-reconcile on a self-rescheduling timer has no such gap — the next startup or midnight pass repairs it.

## Consequences

- The controller re-pushes on three occasions: integration **startup**, each local **midnight** (catching the flip the moment the derived photoperiod shrinks), and **config save**. Because the write is conditional on a diff, the steady-state cost is a cheap comparison, not a device write, every midnight.
- Robust across downtime: an HA outage across the flip midnight self-heals on the next startup or midnight pass, rather than silently leaving a stale schedule until the next config edit. This is the property the edge-triggered alternatives lack.
- The idempotent reconcile needs to read the device's current onboard schedule to compute the diff. `ac_infinity` is cloud-polled with latency, so a just-pushed value may not read back immediately; the reconcile must tolerate a transient mismatch (re-push is harmless — it converges) rather than treat every read-back lag as a change.
- This does **not** reintroduce a per-tick control loop. Unlike the plain `switch`/`light` path (live-driven, ADR-0023), the AC Infinity path still writes only on these discrete re-derivation points; the device runs the cycle in between.
